# TinyBase schema migration and versioning: what TinyBase provides

Research date: 2026-08-26.

**Context.** `apps/app/src/appStore.ts` defines buffi's only table today, `expense`, as a single `TablesSchema` (`id`, `title`, `amount`, `createdAt`) passed to `createMergeableStore().setTablesSchema(...)`, persisted locally via `createOpfsPersister` and synced across clients via `createWsSynchronizer` against the relay server described in `docs/research/sync-server-shape.md` (which itself builds on `docs/research/local-first-persistence-survey.md`, section 9, "TinyBase" — the document that originally locked in TinyBase for buffi). As buffi grows past one entity, that `expense` schema will need to change — new cells, removed cells, retyped cells, possibly renamed ones — in a store that already has data persisted on disk (OPFS) and already syncing with other clients over WebSocket. This document is pure research into what TinyBase itself provides for that situation (schema mutation, persister load-time behavior, sync-time behavior, and any built-in migration/versioning primitives) versus what is undocumented or absent. It draws no conclusions about what buffi should build and makes no recommendations — see the closing Summary for a factual recap only.

**Method.** All claims below are sourced from tinybase.org docs pages (guides and API reference, fetched directly) and the `tinyplex/tinybase` GitHub repository — `readme.md`, `releases.md` (TinyBase's changelog; the repo has no file literally named `CHANGELOG.md`, only lowercase `releases.md` at the root, rendered on the docs site as [tinybase.org/guides/releases](https://tinybase.org/guides/releases/)), and TypeScript source under `src/` (fetched via `raw.githubusercontent.com/tinyplex/tinybase/main/...`), read directly where the docs did not fully resolve a question (specifically: what the runtime schema-validation code actually does to a cell/row/table that doesn't match the current `TablesSchema`, and whether the synchronizer wire protocol carries schema data). No blogs, no Stack Overflow, no secondary write-ups about TinyBase were consulted. The latest published release at research time is **v9.5.1** (2026-08-15) — [github.com/tinyplex/tinybase/releases](https://github.com/tinyplex/tinybase/releases). Source line numbers cited below are against the `main` branch as fetched on 2026-08-26 and may drift as the repo evolves.

## 1. Adding, retyping, removing, and "renaming" cells/tables on a live `TablesSchema`

`setTablesSchema` can be called at any time on a `Store` or `MergeableStore`, including one that already holds data and/or already had a different schema — it is not a one-time, pre-data-load-only operation, though the guide's own example applies it "prior to loading data" as the common case — [tinybase.org/guides/schemas/using-schemas](https://tinybase.org/guides/schemas/using-schemas/). The API reference for `setTablesSchema` states plainly that calling it "may result in a change to data in the Store, as defaults are applied or as invalid Table, Row, or Cell objects are removed" and that this "will fire any listeners to that data, as expected" — [tinybase.org/api/mergeable-store/interfaces/mergeable/mergeablestore/methods/setter/settablesschema](https://tinybase.org/api/mergeable-store/interfaces/mergeable/mergeablestore/methods/setter/settablesschema/) (available since v3.0.0). Source confirms this is not lazy/on-read: `setTablesSchema` in `src/store/index.ts` — when the store already has tables (`!collIsEmpty(tablesMap)`) — immediately re-fetches all existing tables, deletes them, and re-sets them through the new schema (`getTables()` → `delTables()` → `setTables(tables)`), forcing every existing row through the new schema's validation synchronously inside the same transaction — [github.com/tinyplex/tinybase/blob/main/src/store/index.ts#L2070-L2083](https://github.com/tinyplex/tinybase/blob/main/src/store/index.ts#L2070-L2083).

That re-validation pipeline (`validateTables` → `validateTable` → `validateRow` → `getValidatedCell`) is the same code used for every mutation, not a special "migration" path — [github.com/tinyplex/tinybase/blob/main/src/store/index.ts#L507-L615](https://github.com/tinyplex/tinybase/blob/main/src/store/index.ts#L507-L615). Reading it directly answers each operation:

- **Adding a cell** (with a `default`): existing rows are retroactively given the default value for the new cell — the guide demonstrates this exact case, "the `TablesSchema` gains a new defaulted field that is added to the current `Row` to make it compliant" — [tinybase.org/guides/schemas/using-schemas](https://tinybase.org/guides/schemas/using-schemas/). In source, a cell with a declared `default` is placed in a `rowDefaulted` cache and is applied to every row lacking it — [github.com/tinyplex/tinybase/blob/main/src/store/index.ts#L738-L757](https://github.com/tinyplex/tinybase/blob/main/src/store/index.ts#L738-L757) (`setValidTablesSchema`).
- **Removing a cell** from the schema: any existing value under that cell id is treated the same as any other cell id absent from the new schema — an "extra" cell — and is dropped from every row (`getValidatedCell` falls into its "cell id not found in this table's schema" branch, which calls `cellInvalid(...)` with no defaulted-cell argument, i.e. `undefined`, and `objValidate` then deletes that key from the row) — [github.com/tinyplex/tinybase/blob/main/src/store/index.ts#L552-L610](https://github.com/tinyplex/tinybase/blob/main/src/store/index.ts#L552-L610), [github.com/tinyplex/tinybase/blob/main/src/common/obj.ts#L156-L170](https://github.com/tinyplex/tinybase/blob/main/src/common/obj.ts#L156-L170).
- **Retyping a cell** (changing its declared `type`): TinyBase does not coerce/cast the old values to the new type — the "Using Schemas" guide states directly, "The `TablesSchema` does not attempt to cast data" — [tinybase.org/guides/schemas/using-schemas](https://tinybase.org/guides/schemas/using-schemas/). Source confirms: `getValidatedCell` checks the stored value's runtime type against the schema's declared type via `cellOrValueSchemaTypeIncludes`, and on mismatch calls `cellInvalid(tableId, rowId, cellId, cell, cellSchema[DEFAULT])` — [github.com/tinyplex/tinybase/blob/main/src/store/index.ts#L579-L599](https://github.com/tinyplex/tinybase/blob/main/src/store/index.ts#L579-L599). That means a retyped cell's old (now-mismatched) values are replaced with the new type's declared `default` if one exists, or dropped entirely (`undefined`, deleted from the row) if the new `CellSchema` has no `default`.
- **"Renaming" a cell**: there is no rename primitive. A full-text search of the `Store` type definitions and the store implementation for `rename` returns zero matches — [github.com/tinyplex/tinybase/blob/main/src/@types/store/index.d.ts](https://github.com/tinyplex/tinybase/blob/main/src/@types/store/index.d.ts), [github.com/tinyplex/tinybase/blob/main/src/store/index.ts](https://github.com/tinyplex/tinybase/blob/main/src/store/index.ts) — and neither the "Using Schemas" guide nor the API reference for `TablesSchema`/`CellSchema` mentions renaming — [tinybase.org/guides/schemas/using-schemas](https://tinybase.org/guides/schemas/using-schemas/), [tinybase.org/api/store/type-aliases/schema/tablesschema](https://tinybase.org/api/store/type-aliases/schema/tablesschema/). A rename is therefore, as expected, modeled as remove-old-cell-id + add-new-cell-id, with the same mechanics as above applied independently to each: the old cell id's data is dropped (per "removing a cell," above) with **no automatic carry-over** of its value to the new cell id — nothing in `setTablesSchema` reads an old cell's value and writes it under a new id. Any such carry-over would have to be done by the caller (e.g. reading old values and writing them under the new id before or after calling `setTablesSchema`).
- **Removing/renaming a whole table**: if a table id present in the store is not declared in the new `TablesSchema` at all, `validateTable` calls `cellInvalid(tableId)` (with no row/cell arguments) as soon as the table is checked, and the entire table is deleted, not just individual rows — [github.com/tinyplex/tinybase/blob/main/src/store/index.ts#L510-L519](https://github.com/tinyplex/tinybase/blob/main/src/store/index.ts#L510-L519).
- **Row-level cascade**: `validateRow` also enforces that every cell id marked `required: true` **and with no `default`** is present after defaults are applied (tracked in a `rowRequiredNonDefaulted` set built when the schema is set) — [github.com/tinyplex/tinybase/blob/main/src/store/index.ts#L544-L548](https://github.com/tinyplex/tinybase/blob/main/src/store/index.ts#L544-L548), [github.com/tinyplex/tinybase/blob/main/src/store/index.ts#L738-L757](https://github.com/tinyplex/tinybase/blob/main/src/store/index.ts#L738-L757). If a cell is required but undefaulted and its value was just dropped (e.g. by a retype with no matching default), the whole row is removed, not just that cell — confirming the CellSchema docs' note that "a valid default means that the Cell will always be present in a Row" (i.e., `required` only matters at the row level for cells that have no `default`) — [tinybase.org/api/store/type-aliases/schema/cellschema](https://tinybase.org/api/store/type-aliases/schema/cellschema/). Concretely, in buffi's current schema (`apps/app/src/appStore.ts`), `id`, `title`, and `amount` are `required: true` with no `default`, while `createdAt` is `required: true` but also has `default: UNKNOWN_TIMESTAMP` — mechanically, only `id`/`title`/`amount` can trigger a whole-row drop this way; `createdAt` cannot, because it always gets defaulted back in.

None of this is gated behind a dry-run or confirmation step: `setTablesSchema` mutates the live store's data synchronously and silently (beyond firing regular/invalid-data listeners — see §5) the moment it's called.

## 2. Loading persisted OPFS data against a changed schema

There is no separate "migrate on load" code path in the `Persister` framework — loading persisted JSON into a store applies the exact same schema-validated setters as any other mutation, which means §1's rules govern this case identically. Tracing the code: `createOpfsPersister` builds a generic persister via the shared `createCustomPersister` machinery — [tinybase.org/api/persister-browser/functions/creation/createopfspersister](https://tinybase.org/api/persister-browser/functions/creation/createopfspersister/) (available since v6.7.0). That shared machinery picks, per store type, which store method loads persisted content back in: for a plain `Store` it calls `store.setContent`; for a `MergeableStore` (buffi's case — `createMergeableStore()` in `appStore.ts`) it calls `store.setDefaultContent` — [github.com/tinyplex/tinybase/blob/main/src/persisters/common/create.ts#L82-L124](https://github.com/tinyplex/tinybase/blob/main/src/persisters/common/create.ts#L82-L124). `MergeableStore.setDefaultContent` is a thin wrapper — it opens a transaction, sets an internal `defaultingContent` flag (which affects how the incoming data's HLC/merge metadata is treated, not its schema validation), and then calls the same underlying `store.setContent(content)` used everywhere else — [github.com/tinyplex/tinybase/blob/main/src/mergeable-store/index.ts#L761-L772](https://github.com/tinyplex/tinybase/blob/main/src/mergeable-store/index.ts#L761-L772). `setContent` in turn runs through the identical `validateTables`/`validateRow`/`getValidatedCell` pipeline described in §1.

Practically, for `apps/app/src/appStore.ts`'s actual sequence — `createMergeableStore().setTablesSchema(appStoreTablesSchema)` is called **before** `createOpfsPersister` is constructed and `startAutoPersisting()` runs — this means: whatever schema is active on the store at the moment the persister's `load()` runs is the schema that persisted JSON gets validated against, regardless of what schema (if any) was active when that JSON was originally saved. A cell in the saved JSON that doesn't match the *current* schema's declared type, or isn't declared in the current schema at all, is defaulted or dropped exactly as in §1 — including whole-row or whole-table drops if that cascades — with **no coercion attempted** ("The `TablesSchema` does not attempt to cast data" — [tinybase.org/guides/schemas/using-schemas](https://tinybase.org/guides/schemas/using-schemas/)) and no error thrown by default (see §5 for the listener-based way to observe this). The `createOpfsPersister` API page and the general "An Intro To Persistence" guide do not themselves discuss schema-mismatch behavior at all — the only general caution given is: "you should always comprehensively test your persistence strategy to understand the opportunity for data loss" — [tinybase.org/guides/persistence/an-intro-to-persistence](https://tinybase.org/guides/persistence/an-intro-to-persistence/).

## 3. `MergeableStore` sync between clients running different `TablesSchema` versions

Schema is not part of TinyBase's sync/merge protocol at all — it is applied purely locally, independently by each client, to whatever raw table/cell data arrives over the wire. This is confirmed at both the docs and source level:

- **Docs**: "Using A MergeableStore" describes the metadata a `MergeableStore` tracks for CRDT merging as, per update, "a timestamp, based on a hybrid logical clock (HLC), and a hash" — [tinybase.org/guides/synchronization/using-a-mergeablestore](https://tinybase.org/guides/synchronization/using-a-mergeablestore/). Neither that guide nor "Using A Synchronizer" mentions schema as part of that metadata, nor discusses what happens when peers' schemas differ — [tinybase.org/guides/synchronization/using-a-synchronizer](https://tinybase.org/guides/synchronization/using-a-synchronizer/).
- **Source, wire protocol**: the synchronizer message-type enum — shared by every synchronizer implementation (`synchronizer-ws-client`, `synchronizer-ws-server`, `synchronizer-ws-server-simple`, `synchronizer-broadcast-channel`, `synchronizer-local`) — defines exactly eight message kinds: `Response`, `GetContentHashes`, `ContentHashes`, `ContentDiff`, `GetTableDiff`, `GetRowDiff`, `GetCellDiff`, `GetValueDiff` — [github.com/tinyplex/tinybase/blob/main/src/@types/synchronizers/index.d.ts#L8-L25](https://github.com/tinyplex/tinybase/blob/main/src/@types/synchronizers/index.d.ts#L8-L25). None of these carry schema information — the protocol is entirely about content hashes and table/row/cell/value diffs.
- **Source, implementation**: a full-text search for the word "schema" across the entire synchronizer implementation — the shared `src/synchronizers/common.ts` (810 lines) plus all five synchronizer subpackages' `index.ts` files — returns **zero matches** — [github.com/tinyplex/tinybase/blob/main/src/synchronizers/common.ts](https://github.com/tinyplex/tinybase/blob/main/src/synchronizers/common.ts), [github.com/tinyplex/tinybase/tree/main/src/synchronizers](https://github.com/tinyplex/tinybase/tree/main/src/synchronizers). The synchronization layer moves raw content/diffs and never inspects or enforces any `TablesSchema`/`ValuesSchema`.

Combined with §1/§2's finding that schema validation is applied by the same `store.setContent`/row-mutation pipeline for *every* write into a store — whether that write originates locally, from a `Persister` load, or from an incoming synced diff being applied by a `Synchronizer` — the practical consequence (mechanically, from the source read above; not stated as such in any single doc page) is: each connected client validates incoming synced data against **its own, locally-configured** `TablesSchema` independently, exactly as it would validate a local write. A client with an older/narrower schema receiving a diff that includes a cell id or table id its own schema doesn't declare would drop that data per §1's "removing a cell"/"removing a table" rules; a client with no schema at all (`hasTablesSchema` false, per the conditional at [github.com/tinyplex/tinybase/blob/main/src/store/index.ts#L558-L611](https://github.com/tinyplex/tinybase/blob/main/src/store/index.ts#L558-L611)) applies only basic type/serializability checks, not per-cell schema constraints, to the same incoming data. There is no handshake, negotiation, or agreement step between peers about schema before or during sync.

## 4. Built-in schema-versioning / migration primitives

TinyBase ships no schema version field, migration function, or upgrade-hook API for evolving a `TablesSchema` over time. Specifically checked and found absent:

- **`CellSchema`/`ValueSchema` fields**: the full set of recognized keys is `type`, `enum`, `default`, `allowNull`, `required` — confirmed both in the docs page ([tinybase.org/api/store/type-aliases/schema/cellschema](https://tinybase.org/api/store/type-aliases/schema/cellschema/)) and in source, where `validateCellOrValueSchema` explicitly rejects any schema key not in that exact list (`arrayHas([TYPE, ENUM, DEFAULT, ALLOW_NULL, REQUIRED], id)`) — [github.com/tinyplex/tinybase/blob/main/src/store/index.ts#L414-L421](https://github.com/tinyplex/tinybase/blob/main/src/store/index.ts#L414-L421). There is no `version` key.
- **Guides index**: the full guides category list at [tinybase.org/guides](https://tinybase.org/guides/) is: The Basics, Building UIs With React, Building UIs With Solid, Building UIs With Svelte, **Schemas** (Using Schemas, Schema-Based Typing, Mutating Data With Listeners, Using Schematizers), Using Middleware, Persistence, Synchronization, Integrations, Using Metrics, Using Indexes, Using Relationships, Using Checkpoints, Using Queries, Inspecting Data, Error Codes, How TinyBase Is Built, FAQ, Agents Guide, Releases. No category or page is titled or scoped to migration, versioning, or schema evolution.
- **"Using Schematizers"**: this guide is the closest-sounding candidate by name but is unrelated — a Schematizer only does one-way, runtime conversion of a *third-party* validation library's schema format (Zod, TypeBox, Valibot, ArkType, Yup, or Effect Schema) into TinyBase's `TablesSchema`/`ValuesSchema` shape; it "provide[s] a convenient way to convert schemas from popular validation libraries into TinyBase's `TablesSchema` and `ValuesSchema` formats" and has no notion of versions or migrating data across schema changes over time — [tinybase.org/guides/schemas/using-schematizers](https://tinybase.org/guides/schemas/using-schematizers/).
- **`releases.md` (the changelog)**: the file has no matches at all for "version" or "upgrade" in a schema-migration sense, and only a handful of "migrat" occurrences, none of which are a schema-versioning feature for end-user `TablesSchema` data. Two representative hits: (a) a v9.x reliability note that "Fragmented Durable Object SQL storage now encodes unsafe and uppercase prefixes collision-free. Previous ambiguous table names are not adopted automatically and must be migrated explicitly" — about internal persister table-naming, not `TablesSchema` — [raw.githubusercontent.com/tinyplex/tinybase/main/releases.md](https://raw.githubusercontent.com/tinyplex/tinybase/main/releases.md); (b) a v7.0 "Migration Guide" section, which is a **release-upgrade guide for TinyBase's own breaking change** (database persisters switched from `hasCell() === false` to `getCell() === null` for missing data, requiring apps to add `allowNull: true` to affected `CellSchema` definitions), not a mechanism for versioning or migrating an application's own schema over time — [tinybase.org/guides/releases](https://tinybase.org/guides/releases/) (v7.0 section), [raw.githubusercontent.com/tinyplex/tinybase/main/releases.md](https://raw.githubusercontent.com/tinyplex/tinybase/main/releases.md).
- **`readme.md`**: zero matches for "migrat", "schema version", or "upgrade" — [raw.githubusercontent.com/tinyplex/tinybase/main/readme.md](https://raw.githubusercontent.com/tinyplex/tinybase/main/readme.md).

## 5. Documented best practices, limitations, and gotchas for changing schemas in a synced, persisted app

TinyBase's docs contain no dedicated guide page or section on evolving schemas over time in an already-persisted or already-synced store — none of the Schemas, Persistence, or Synchronization guide pages address it as a topic. What the docs and source do establish, as caveats implicit in the mechanisms above:

- **Schema changes are silent by default.** `setTablesSchema`'s own reference doc states the operation "may result in a change to data in the Store, as defaults are applied or as invalid Table, Row, or Cell objects are removed" with no confirmation step — [tinybase.org/api/mergeable-store/interfaces/mergeable/mergeablestore/methods/setter/settablesschema](https://tinybase.org/api/mergeable-store/interfaces/mergeable/mergeablestore/methods/setter/settablesschema/). There are also no schema-specific entries in TinyBase's documented Error Codes list — [tinybase.org/guides/error-codes](https://tinybase.org/guides/error-codes/) — so a dropped/defaulted cell does not throw or surface as a catchable error by default.
- **A listener-based observability mechanism does exist**, and is the one documented way to detect schema-driven drops. `addInvalidCellListener` (and its `addInvalidValueListener` counterpart) fire "when invalid data was attempted to be written to a Cell," including — per a `TablesSchema` — cases of "tables not in the schema, cells of wrong types, missing non-defaulted cells, or empty rows without defaults," and can optionally be registered as `mutator` listeners, letting an app "address any failed writes programmatically" — [tinybase.org/api/store/interfaces/store/store/methods/listener/addinvalidcelllistener](https://tinybase.org/api/store/interfaces/store/store/methods/listener/addinvalidcelllistener/) (available since v1.1.0). This exists as a general write-time hook (it also fires for ordinary invalid writes unrelated to schema changes), not a schema-migration-specific API.
- **"Mutating Data With Listeners"** documents the general mutator-listener mechanism (listeners are non-mutating by default; a `mutator: true` flag lets a listener modify Store data, and mutator listeners run before read-only ones) and notes one common reason to define a `TablesSchema` in the first place is "when you are loading data from a source and you want to ensure the data is sculpted as your application require[s]" — but the guide is about validating/correcting individual writes as they happen, not about transforming a whole store's existing data from one schema shape to another — [tinybase.org/guides/schemas/mutating-data-with-listeners](https://tinybase.org/guides/schemas/mutating-data-with-listeners/).
- **Persistence carries a general, non-schema-specific data-loss warning**: "you should always comprehensively test your persistence strategy to understand the opportunity for data loss" — [tinybase.org/guides/persistence/an-intro-to-persistence](https://tinybase.org/guides/persistence/an-intro-to-persistence/). This is stated as general persister-testing advice, not schema-change-specific guidance.
- No guide page discusses coordinating schema changes across multiple already-synced clients, or sequencing/order-of-operations for changing a schema in a store that is both persisted and actively syncing.

## Summary

**Supported, and confirmed from primary sources:**
- `setTablesSchema` can be called at any time on a live `Store`/`MergeableStore`, including one with existing data, and immediately re-validates that data against the new schema in the same transaction.
- Adding a cell with a `default` retroactively backfills that default onto every existing row.
- Removing a cell (or a whole table) from the schema drops that data on the next validation pass (`setTablesSchema` call, `Persister` load, or incoming sync diff).
- Retyping a cell drops or re-defaults mismatched existing values — TinyBase explicitly does not cast/coerce between types.
- A row that ends up missing a `required`-and-undefaulted cell after validation is dropped in its entirety, not just that cell.
- `Persister.load()` (including `createOpfsPersister`) and `MergeableStore.setDefaultContent()` (used internally by persisters for `MergeableStore`s) both route through the identical schema-validated store-mutation pipeline as any other write — there is no separate, more lenient "loading old data" code path.
- The synchronizer wire protocol (message types confirmed from `@types/synchronizers/index.d.ts`, and a zero-hit full-text search for "schema" across all synchronizer source) carries only content hashes and table/row/cell/value diffs — never schema. Each client applies its own local schema to incoming synced data independently.
- `addInvalidCellListener`/`addInvalidValueListener` are a documented, general-purpose (not migration-specific) way to observe or programmatically react to data a schema rejects.

**Not supported / not found, checked explicitly:**
- No built-in cell/table rename operation (zero matches for "rename" across the `Store` type definitions and implementation) — a rename is remove+add with no automatic value carry-over.
- No schema `version` field, migration function, or upgrade-hook API — `CellSchema`/`ValueSchema` accept only `type`, `enum`, `default`, `allowNull`, `required`.
- No guides-index category or page for schema migration/versioning; the "Using Schematizers" guide is an unrelated third-party-schema-format converter.
- No schema-migration content in `readme.md`; the "Migration Guide" that does exist in `releases.md` (v7.0) is about upgrading application code across a TinyBase library release, not about versioning an app's own `TablesSchema`.
- No Error Codes entries for schema violations, and no dedicated docs guidance on sequencing schema changes across an already-persisted and/or already-synced deployment.
