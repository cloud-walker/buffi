# Local-first persistence survey

Research date: 2026-08-08. This document supports GitHub issue "Survey local-first technologies" (#2), child of "Local-first persistence for Expense" (#1) in `cloud-walker/buffi`.

**Context.** Buffi (`apps/app`) is a React 19 + Vite + Panda CSS SPA with **no backend today**. The only domain resource is `Expense { id, title, amount }` ([domain-model.md](/Users/cw/dev/buffi/docs/domain-model.md)). All data is currently fake, generated via a faker mock factory. Deploys go to Railway via `railway up` (no GitHub↔Railway integration — an established convention). The team is open to standing up a **new** Railway backend service if a chosen technology needs one; there is no zero-backend constraint, just a strong preference not to build more infrastructure than necessary right now.

**Method.** All claims below are sourced from official docs sites, GitHub repos (via the GitHub API, checked 2026-08-08), npm registry metadata, and first-party pricing pages — no blogs, no secondary write-ups. Every factual claim is cited inline.

**Evaluation priority** (team-set, in order): (1) ease/speed of integration into the existing no-backend React+Vite SPA, (2) cost / infrastructure control, (3) offline robustness / conflict-resolution quality.

## 1. RxDB

- **Data model**: NoSQL/document database with JSON Schema-defined collections, running client-side ("a NoSQL database for JavaScript that runs directly in your app") — [rxdb.info](https://rxdb.info/).
- **Backend requirement**: None to start — "You can even run your app entirely without a backend" ([rxdb.info](https://rxdb.info/)). When sync is needed, RxDB replicates against an existing backend (REST/GraphQL/etc.) or its own optional **RxServer** plugin, which runs as a Node/Deno/Bun/Electron process on top of Express, Fastify, or Koa and is self-hostable, though the server plugin itself ships under the SSPL rather than the core's Apache-2.0 license ([rxdb.info/rx-server](https://rxdb.info/rx-server.html)).
- **Maturity/community**: Created December 2016, **23,315 GitHub stars**, most recent push 2026-08-07, latest release **17.4.0** (2026-07-13) — [github.com/pubkey/rxdb](https://github.com/pubkey/rxdb). One of the oldest projects surveyed.
- **Cost**: Core is free forever (Apache-2.0). Paid "Premium" plugins: **Pro $99/mo** (annual) unlocks OPFS/IndexedDB/SQLite storage engines, encryption, fulltext search; **Pro Plus $239/mo** adds performance plugins and Fastify/Koa server adapters; **Enterprise** is custom-priced — [rxdb.info/premium](https://rxdb.info/premium/).
- **TypeScript**: First-class; TypeScript is listed as a core concept and the repo is >4.4M bytes TypeScript vs. ~134K JavaScript ([github.com/pubkey/rxdb](https://github.com/pubkey/rxdb)).
- **Conflict handling**: Client-side, developer-supplied `conflictHandler` set via `addCollection()`; the **default handler always drops the local "fork" and takes the master/server state** rather than auto-merging — deterministic and safe, but not a CRDT, so silent data loss on conflict is possible unless you write custom merge logic — [rxdb.info/replication](https://rxdb.info/replication.html).

## 2. ElectricSQL (now "Electric")

- **Data model**: Postgres-native — Electric is explicitly "a read-path sync engine for Postgres," syncing rows out to clients via a "Shape" primitive; it is not a standalone document/CRDT store — [electric.ax/docs/intro](https://electric.ax/docs/intro).
- **Backend requirement**: **Yes, and it's non-trivial** — requires an existing Postgres database with logical replication enabled and a `REPLICATION`-privileged connection. The sync service is an Elixir application, published as a Docker image (`electricsql/electric`), self-hostable on AWS/Cloudflare/DigitalOcean/Fly.io/GCP/Netlify/etc. — [electric.ax/docs/api/config](https://electric.ax/docs/api/config). Critically, **Electric does not do write-path sync at all**: "It doesn't provide (or prescribe) a built-in solution for getting data back into Postgres" — you must build writes/conflict-handling yourself using one of four suggested patterns — [electric.ax/docs/guides/writes](https://electric.ax/docs/guides/writes).
- **Maturity/community**: Created June 2022, **10,303 GitHub stars**, pushed 2026-08-05, client library on npm at v1.5.25 (2026-08-04) — [github.com/electric-sql/electric](https://github.com/electric-sql/electric). Notably, the project **rebranded from "ElectricSQL" to "Electric"** and its GitHub description now reads "The agent platform built on sync" rather than a local-first-database pitch — a real strategic-direction risk for a team evaluating it as local-first infra — [github.com/electric-sql/electric](https://github.com/electric-sql/electric).
- **Cost**: Electric Cloud advertises "usage-based" pricing with a "generous free tier," but the product page does not state concrete free-tier limits or paid prices — [electric.ax/product/cloud](https://electric.ax/product/cloud). Self-hosting is free (Docker + your own Postgres).
- **TypeScript**: Client library is TypeScript; core sync service is Elixir, not JS/TS — [electric.ax/docs/intro](https://electric.ax/docs/intro).
- **Conflict handling**: None built-in for writes — fully delegated to the application. Docs explicitly note "blunt strategies... can be much easier to implement and reason about" as an acceptable fallback — [electric.ax/docs/guides/writes](https://electric.ax/docs/guides/writes).

## 3. PowerSync

- **Data model**: Relational/SQL — PowerSync replicates an existing backend database into an embedded SQLite instance on the client. Backend databases supported: **Postgres, MongoDB, MySQL (beta), SQL Server (beta), Convex (experimental)** — [docs.powersync.com/intro/powersync-overview](https://docs.powersync.com/intro/powersync-overview).
- **Backend requirement**: **Yes** — you must already have (or stand up) one of the supported backend databases, plus the PowerSync Service itself. The service is Docker-deployable (`journeyapps/powersync-service` on Docker Hub) and there is a free, source-available **"Open Edition"** for self-hosting — [docs.powersync.com/self-hosting/getting-started](https://docs.powersync.com/self-hosting/getting-started). PowerSync explicitly documents Railway as a deployment target and offers an official one-click "PowerSync Starter (Postgres)" Railway template — [railway.com/deploy/powersync-starter-postgres](https://railway.com/deploy/powersync-starter-postgres).
- **Maturity/community**: JS SDK repo created October 2023, **704 GitHub stars**, pushed 2026-08-06, latest npm `@powersync/web` v2.1.1 (2026-08-05) — [github.com/powersync-ja/powersync-js](https://github.com/powersync-ja/powersync-js).
- **Cost**: **Free** cloud plan (2GB synced/mo, 500MB hosted data, 50 connections, 2 instances, projects deactivate after a week idle); **Pro from $49/mo** (30GB synced, 10GB storage, 1,000 connections); **Team from $599/mo**; **Enterprise** custom. Self-hosted **Open Edition is free**, though the web dashboard is not available when self-hosting — [powersync.com/pricing](https://www.powersync.com/pricing), [docs.powersync.com/self-hosting/getting-started](https://docs.powersync.com/self-hosting/getting-started).
- **TypeScript**: SDKs are TypeScript (JS Web SDK repo is >1.6M bytes TS) — [github.com/powersync-ja/powersync-js](https://github.com/powersync-ja/powersync-js).
- **Conflict handling**: Default is **per-field last-write-wins** ("the last update ... to each individual field wins," deletes win over updates); fully customizable at the app-backend level; PowerSync also supports syncing **Yjs CRDT** payloads for automatic merge in collaborative scenarios — [docs.powersync.com/usage/lifecycle-maintenance/handling-update-conflicts](https://docs.powersync.com/usage/lifecycle-maintenance/handling-update-conflicts).

## 4. Zero (Rocicorp)

- **Data model**: Relational/SQL — zero-cache maintains a read-only replica of an upstream **Postgres** database and syncs normalized query results into a local client store — [zero.rocicorp.dev/](https://zero.rocicorp.dev/).
- **Backend requirement**: **Yes** — Zero assumes an existing Postgres database as source of truth, replicated to it. It is fully open-source and self-hostable: Docker images on Docker Hub (`rocicorp/zero`) and GHCR, with documented Docker Compose, Fly.io, AWS/SST, and Kubernetes deployment paths; "the simplest way to deploy Zero is to run everything on a single node... the least expensive way" — [zero.rocicorp.dev/docs/deployment](https://zero.rocicorp.dev/docs/deployment). No Railway-specific guide is published, but the generic Docker Compose setup is portable to Railway.
- **Maturity/community**: Repo created February 2023, **3,349 GitHub stars**, pushed 2026-08-08 (today), latest npm `@rocicorp/zero` v1.8.0 (2026-07-13) — [github.com/rocicorp/mono](https://github.com/rocicorp/mono). Backed by Rocicorp (also behind Replicache). Documented production users include **tldraw, Tines, OpenCode, Productlane, and Shortcut**, plus a demo syncing a 1.2M-row issue tracker — [zero.rocicorp.dev/](https://zero.rocicorp.dev/).
- **Cost**: Open source and free to self-host. A managed offering exists ("can run on either your servers or ours") but no public price list was found on primary sources — [zero.rocicorp.dev/](https://zero.rocicorp.dev/).
- **TypeScript**: Native — the mono-repo is >13.4M bytes TypeScript, dominant over all other languages — [github.com/rocicorp/mono](https://github.com/rocicorp/mono).
- **Conflict handling**: Not CRDT-based. Writes go through **custom mutators using "server reconciliation"** (a technique borrowed from video-game netcode): the mutator runs optimistically on the client, then authoritatively re-runs on the server; if the server rejects it, the optimistic client state is rolled back — [zero.rocicorp.dev/docs/mutators](https://zero.rocicorp.dev/docs/mutators). This gives strong app-level control but requires you to design mutator logic thoughtfully for offline correctness.

## 5. Triplit

- **Data model**: Full-stack "syncing database" combining relational querying with CRDT-based collaborative primitives; runs on both client and server with pluggable storage (IndexedDB, SQLite, Durable Objects) — [github.com/aspen-cloud/triplit README](https://raw.githubusercontent.com/aspen-cloud/triplit/main/README.md).
- **Backend requirement**: Yes, a dedicated sync server, but it is **self-hostable**: each release ships a Docker image (`aspencloud/triplit-server`), deployable to any Docker-capable host (AWS, GCP, Azure, DigitalOcean, or your own infra) — [triplit.dev/docs/self-hosting](https://www.triplit.dev/docs/self-hosting) (via search-result confirmation; the page itself returned a transient fetch error during this research), [github.com/aspen-cloud/triplit](https://github.com/aspen-cloud/triplit).
- **Maturity/community**: Repo created July 2023, **3,103 GitHub stars**, but **last pushed 2026-01-19** — roughly seven months stale as of this research — and the last published package (`@triplit/solid`) shipped 2025-07-31, over a year old — [github.com/aspen-cloud/triplit](https://github.com/aspen-cloud/triplit); npm `@triplit/client` latest 1.0.50, also 2025-07-31. This is a meaningful activity slowdown relative to every other packaged product surveyed.
- **Cost**: Triplit Cloud advertises "start free, scale as you grow" and a 30-day free trial for production use, per site search results; the pricing page itself (triplit.dev/pricing) could not be reached during this research (repeated fetch failures) — [triplit.dev](https://www.triplit.dev/pricing). Self-hosting the open-source server is free.
- **TypeScript**: First-class — the repo is >2.6M bytes TypeScript, and schemas provide "Typescript autocompletion" — [github.com/aspen-cloud/triplit README](https://raw.githubusercontent.com/aspen-cloud/triplit/main/README.md).
- **Conflict handling**: CRDT-based — "uses CRDTs (Conflict-free Replicated Data Types) to enable collaborative, multiplayer functionality," with property-level conflict resolution and automatic reconnection/consistency guarantees — [github.com/aspen-cloud/triplit README](https://raw.githubusercontent.com/aspen-cloud/triplit/main/README.md).

## 6. LiveStore

- **Data model**: Event-sourced — an append-only eventlog is the source of truth; deterministic "materializers" derive SQLite-backed state from events — [docs.livestore.dev/reference/concepts](https://docs.livestore.dev/reference/concepts/).
- **Backend requirement**: Yes, a sync backend is required and is treated as a core building block, not optional — [docs.livestore.dev](https://docs.livestore.dev/). The default/primary provider targets **Cloudflare Workers + Durable Objects**; alternative providers exist for **ElectricSQL** and **S2**, and a "build your own sync provider" API exists, but there is no documented generic self-hostable Node.js sync server — [docs.livestore.dev/reference/syncing/sync-provider](https://docs.livestore.dev/reference/syncing/sync-provider/).
- **Maturity/community**: Repo created September 2023, **3,661 GitHub stars**, pushed 2026-08-07, latest release **v0.4.0** (2026-06-02) — [github.com/livestorejs/livestore](https://github.com/livestorejs/livestore). Critically, LiveStore's own docs state: **"LiveStore is currently in beta... LiveStore is not yet ready for all production scenarios,"** with **no timeline for a 1.0 release** — [docs.livestore.dev/evaluation/state-of-the-project](https://docs.livestore.dev/evaluation/state-of-the-project/). The flagship production use is Overtone, built by the LiveStore team itself.
- **Cost**: No LiveStore-specific hosted pricing; cost is whatever the chosen sync provider (e.g., Cloudflare Workers/Durable Objects/D1) charges.
- **TypeScript**: Native — repo is >3.25M bytes TypeScript — [github.com/livestorejs/livestore](https://github.com/livestorejs/livestore).
- **Conflict handling**: Not CRDT — relies on **centrally-ordered events + deterministic materializers**, with local pending events "rebased on top of newly pulled upstream events" when reconnecting — convergent by construction but not a CRDT, and no explicit merge semantics beyond event ordering — [docs.livestore.dev/reference/concepts](https://docs.livestore.dev/reference/concepts/).

## 7. Jazz

- **Data model**: **Currently in flux.** The live jazz.tools site describes Jazz as "a local-first relational database with row-level permissions" — [jazz.tools/docs](https://jazz.tools/docs). This is a **new v2 architecture**, publicly announced as alpha, that replaced the original CRDT-based "CoValues"/cojson model: Jazz "underwent a significant redesign that moved away from CRDT replay toward a more relational, ORM-like query shape" — [jazz.tools/blog/what-is-jazz](https://jazz.tools/blog/what-is-jazz). The old CRDT product still exists as **"classic Jazz"** at a separate domain and is being phased out in favor of migration to v2 — [jazz.tools/blog/what-is-jazz](https://jazz.tools/blog/what-is-jazz).
- **Backend requirement**: Yes — either the hosted **Jazz Cloud** or a self-hosted sync server via the `jazz-run` Node.js package (requires Node ≥20) — [jazz.tools/docs](https://jazz.tools/docs) (via search-result confirmation of `jazz-run`).
- **Maturity/community**: The current GitHub repo shows **147 stars** and was **created 2026-01-04** — [github.com/garden-co/jazz](https://github.com/garden-co/jazz) — consistent with a recent repository reset tied to the v2 rewrite, so star count is not representative of the project's multi-year history. Jazz v2 is explicitly **alpha**: "adopters should expect an evolving API and a best-effort SLA," suitable for "adventurous greenfield teams" — [jazz.tools/blog/what-is-jazz](https://jazz.tools/blog/what-is-jazz).
- **Cost**: Jazz Cloud is usage-based — **Compute $0.039/hr** (2GB RAM instance), **Storage $0.45/GB/mo**, **Egress $0.09/GB**, with a free tier (1GB RAM, 1GB/mo storage, 5GB/mo egress) — [jazz.tools/](https://jazz.tools/).
- **TypeScript**: Native — repo top languages are Rust (6.8M bytes) then TypeScript (3.5M bytes) — [github.com/garden-co/jazz](https://github.com/garden-co/jazz).
- **Conflict handling**: **Last-writer-wins at the row/field level**, backed by a "row-version-history" model that keeps losing versions in history for potential future reconciliation — explicitly **not** described as CRDT-based in current docs, a departure from the original CoValues CRDT design — [jazz.tools/docs/concepts/local-first-data-model](https://jazz.tools/docs/concepts/local-first-data-model) (content also echoed at [jazz.tools/blog/what-is-jazz](https://jazz.tools/blog/what-is-jazz)).

## 8. Instant (InstantDB)

- **Data model**: Entity-based schema with typed fields and relational "links" between entities, defined in TypeScript (`i.string()`, `i.boolean()`, etc.) — [instantdb.com/docs](https://www.instantdb.com/docs).
- **Backend requirement**: Instant is normally used against Instant's own hosted backend (nothing to stand up to start), but it is **also self-hostable** — the docs include dedicated VPS and AWS self-hosting guides. The self-hosted server is configured via `JAVA_OPTS` and uses Hazelcast for horizontal scaling, indicating a JVM-based (Clojure) backend — [instantdb.com/docs/self-hosting](https://www.instantdb.com/docs/self-hosting). The GitHub repo is majority TypeScript with a large Clojure component (backend), confirming this — [github.com/instantdb/instant](https://github.com/instantdb/instant).
- **Maturity/community**: Repo created August 2024, **10,383 GitHub stars**, pushed 2026-08-08 (today); npm `@instantdb/react` latest **1.0.63**, published 2026-08-07 — very active, near-daily release cadence — [github.com/instantdb/instant](https://github.com/instantdb/instant).
- **Cost**: **Free** ($0, 1GB db space, unlimited API requests, 1 team member/app, "free projects are never paused"); **Pro $30/mo** (10GB then $0.125/GB overage, priority support, 10 team members, 7-day backups); **Startup $600/mo** (250GB); **Enterprise** custom — [instantdb.com/pricing](https://www.instantdb.com/pricing).
- **TypeScript**: First-class — schemas and client are TypeScript-native, and the repo is predominantly TypeScript (~4.8M bytes) — [github.com/instantdb/instant](https://github.com/instantdb/instant).
- **Conflict handling**: Field/attribute-level merge rather than full CRDT: a plain `update` overwrites a whole attribute and "risks clobbering changes made by other clients," while a `merge` operation lets you patch a nested slice of a JSON attribute so concurrent clients can update different keys without overwriting each other — effectively **granular last-write-wins with an opt-in deep-merge helper** — [instantdb.com/docs/instaml](https://www.instantdb.com/docs/instaml).

## 9. TinyBase

- **Data model**: Reactive, local-first "tabular and key-value" store (not documents, not full SQL) — [tinybase.org/guides/the-basics](https://tinybase.org/guides/the-basics/).
- **Backend requirement**: **None required.** TinyBase is "local-first... operating as an in-memory data store without requiring a backend by default" — [tinybase.org/guides/the-basics](https://tinybase.org/guides/the-basics/). When multi-client sync is wanted, it ships `WsSynchronizer` (client) and `createWsServer` (a small self-hostable Node.js WebSocket server) for client-server sync, or peer-to-peer sync via `BroadcastChannel` — [tinybase.org/guides/the-basics/architectural-options](https://tinybase.org/guides/the-basics/architectural-options/). A lightweight Node WS server is trivially deployable as a Railway service. Third-party persisters also exist for ElectricSQL, PowerSync, Yjs, and Automerge if deeper backend integration is later desired.
- **Maturity/community**: Repo created December 2021, **5,139 GitHub stars**, pushed 2026-08-08 (today), latest release **v9.4.0** published the same day — extremely active — [github.com/tinyplex/tinybase](https://github.com/tinyplex/tinybase).
- **Cost**: **Fully free**, MIT-licensed, "no hosted product, no paid tier, no telemetry and no sign-up" — [github.com/tinyplex/tinybase/blob/main/LICENSE](https://github.com/tinyplex/tinybase/blob/main/LICENSE) (license confirms MIT; no pricing page exists on tinybase.org, consistent with the "no paid tier" claim).
- **TypeScript**: Native — repo is TypeScript-majority (3.76M bytes TS vs. 2.75M JS) and the docs include a dedicated "TinyBase and TypeScript" guide — [github.com/tinyplex/tinybase](https://github.com/tinyplex/tinybase), [tinybase.org/guides/the-basics](https://tinybase.org/guides/the-basics/).
- **Conflict handling**: **CRDT-based.** The `MergeableStore` interface records metadata per cell/value so changes can be reconciled automatically; TinyBase's docs describe the resulting last-write-wins merge, applied at single-cell granularity, as making `MergeableStore` "act as a Conflict-Free Replicated Data Type (CRDT)" — cell-level granularity minimizes real conflicts even though the underlying rule is LWW rather than a multi-value CRDT — [tinybase.org/guides/the-basics/architectural-options](https://tinybase.org/guides/the-basics/architectural-options/).

## 10. WatermelonDB

- **Data model**: SQLite-backed relational database with a decorator-based Model/ORM layer (`@field()`, `@children()`), built primarily for React and React Native apps — [github.com/Nozbe/WatermelonDB README](https://raw.githubusercontent.com/Nozbe/WatermelonDB/master/README.md).
- **Backend requirement**: WatermelonDB explicitly ships **no backend at all**: "Watermelon is only a local database — you need to bring your own backend," implementing a documented pull/push HTTP sync protocol yourself — [watermelondb.dev/docs/Sync/Backend](https://watermelondb.dev/docs/Sync/Backend).
- **Maturity/community**: Repo created August 2018, **11,765 GitHub stars**, but **last pushed 2025-08-11** — about a year stale as of this research — and latest stable npm release **0.28.0** shipped 2025-04-07 — [github.com/Nozbe/WatermelonDB](https://github.com/Nozbe/WatermelonDB). Documented production users include **Nozbe Teams (creator), Mattermost, Rocket.Chat, CAPMO, Steady, and Aerobotics** — [github.com/Nozbe/WatermelonDB README](https://raw.githubusercontent.com/Nozbe/WatermelonDB/master/README.md).
- **Cost**: Free, open source; no hosted product exists (you own 100% of the backend you write).
- **TypeScript**: Bolted-on rather than native — the docs describe "static typing with **Flow or TypeScript**" (Flow-first historically), and the GitHub language breakdown shows the repo is overwhelmingly plain JavaScript with no significant TypeScript share — [github.com/Nozbe/WatermelonDB](https://github.com/Nozbe/WatermelonDB), [github.com/Nozbe/WatermelonDB README](https://raw.githubusercontent.com/Nozbe/WatermelonDB/master/README.md).
- **Conflict handling**: Record-level, not CRDT. Your backend must reject (abort) a push if a record was modified on the server after the client's `lastPulledAt`, forcing a re-pull; WatermelonDB then reapplies the client's locally-changed columns on top of the fresh server state — effectively **per-column "client wins for what it touched, server wins otherwise"** — [watermelondb.dev/docs/Sync/Backend](https://watermelondb.dev/docs/Sync/Backend).

## 11. Hand-rolled: Automerge and Yjs (build-your-own sync on a CRDT library)

### Automerge

- **Data model**: A CRDT library for **JSON-like documents** that merge automatically under concurrent edits — [automerge.org/docs/hello](https://automerge.org/docs/hello/).
- **Backend requirement**: None inherently — Automerge is network-agnostic ("client/server, e.g. WebSocket, peer-to-peer, e.g. WebRTC, or entirely local, e.g. Bluetooth"); `automerge-repo` provides a common networking/storage abstraction, and the project publishes a reference **`automerge-repo-sync-server`** — a small Node/Express app, self-hostable via Docker (`ghcr.io/automerge/automerge-repo-sync-server`) — trivially deployable to Railway — [automerge.org/docs/hello](https://automerge.org/docs/hello/), [github.com/automerge/automerge-repo-sync-server](https://github.com/automerge/automerge-repo-sync-server).
- **Maturity/community**: Core repo created December 2019, **6,476 GitHub stars**; `automerge-repo` created May 2022, **696 stars**; both pushed within the last day of research — [github.com/automerge/automerge](https://github.com/automerge/automerge), [github.com/automerge/automerge-repo](https://github.com/automerge/automerge-repo). Latest stable npm `@automerge/automerge` is **3.4.0** (2026-07-31).
- **Cost**: Free/open source; only cost is whatever compute you self-host the sync server on.
- **TypeScript**: Mixed — the core algorithm is implemented in **Rust** (compiled to WASM), with a JS/TS wrapper API; repo language breakdown is JavaScript-majority (4.9M bytes) with Rust (3.7M) and TypeScript (510K) — TS bindings exist but are not the implementation language — [github.com/automerge/automerge](https://github.com/automerge/automerge) (language stats via GitHub API).
- **Conflict handling**: True CRDT — concurrent edits merge automatically with no manual conflict resolution required, the strongest offline-robustness guarantee of any candidate surveyed — [automerge.org/docs/hello](https://automerge.org/docs/hello/).

### Yjs

- **Data model**: CRDT "shared types" (`Y.Map`, `Y.Array`, `Y.Text`, etc.) modeled after native JS `Map`/`Array` — [docs.yjs.dev](https://docs.yjs.dev/).
- **Backend requirement**: None required by the library itself — "Yjs doesn't need a central source of truth" — but real apps need a network **provider**. Options include the official, self-hostable **`y-websocket-server`** (small Node app, Docker-buildable, `PORT` env var, intended as a starting point to fork/adapt), or hosted providers (Liveblocks, Y-Sweet, Tiptap Cloud) — [docs.yjs.dev](https://docs.yjs.dev/), [github.com/yjs/y-websocket-server](https://github.com/yjs/y-websocket-server).
- **Maturity/community**: Created July 2014 — **the oldest project surveyed** — **22,318 GitHub stars**, pushed 2026-08-06, latest npm release **13.6.32** (2026-08-04) — [github.com/yjs/yjs](https://github.com/yjs/yjs).
- **Cost**: Free/open source core; cost is whatever you self-host, or a third-party hosted provider's pricing if chosen instead.
- **TypeScript**: **Bolted-on** — the repo is 100% JavaScript with no TypeScript source; type definitions are hand-written `.d.ts` files layered on top, not TS-native — [github.com/yjs/yjs](https://github.com/yjs/yjs) (language stats via GitHub API).
- **Conflict handling**: True CRDT, same category as Automerge — automatic, guaranteed-convergent merging with no app-level conflict logic needed — [docs.yjs.dev](https://docs.yjs.dev/).

## Finalists

Screened out, with reasons:

- **ElectricSQL/Electric, PowerSync, Zero** — all three assume an **existing relational (mostly Postgres) backend database** as the source of truth. For an app with zero backend and one `Expense` entity, that's inverted effort: you'd have to design and deploy a Postgres schema + a dedicated sync service (Elixir/Docker, PowerSync Service, or zero-cache) before writing a single line of sync-aware client code. Reasonable choices later if buffi grows into a proper multi-entity relational app with a Postgres backend already in place, but premature now given priority #1 (ease/speed of integration with no backend today). Electric additionally carries direction risk from its "agent platform" rebrand ([github.com/electric-sql/electric](https://github.com/electric-sql/electric)).
- **Triplit** — technically a strong fit (self-hostable Docker, CRDT, TS-native, no pre-existing backend needed) but shows real momentum concerns: no GitHub push in ~7 months and no package release in over a year as of this research, plus an unreachable pricing page ([github.com/aspen-cloud/triplit](https://github.com/aspen-cloud/triplit)). Risky to build on without more confidence in active maintenance.
- **LiveStore** — by its own docs, **explicitly not production-ready** ("not yet ready for all production scenarios," beta, no 1.0 timeline) ([docs.livestore.dev/evaluation/state-of-the-project](https://docs.livestore.dev/evaluation/state-of-the-project/)), and its default sync path is Cloudflare-specific rather than Railway-friendly.
- **Jazz** — mid-rewrite: v2 is alpha, publicly described as best-effort SLA / evolving API, following a hard pivot away from its original CRDT model ([jazz.tools/blog/what-is-jazz](https://jazz.tools/blog/what-is-jazz)). Too much platform risk for a real (if small) app right now.
- **WatermelonDB** — ships with **no sync protocol implementation at all** (biggest DIY burden of the packaged options), is primarily React-Native-oriented, TypeScript support is secondary to Flow, and the project has been quiet for about a year ([watermelondb.dev/docs/Sync/Backend](https://watermelondb.dev/docs/Sync/Backend), [github.com/Nozbe/WatermelonDB](https://github.com/Nozbe/WatermelonDB)).

That leaves four finalists, spanning "fastest to integrate" to "maximum control":

|                      | RxDB                                                      | InstantDB                                       | TinyBase                                          | Automerge/Yjs (hand-rolled)                                                    |
| -------------------- | --------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------ |
| Backend needed today | No                                                        | No (hosted free tier)                           | No                                                | No                                                                             |
| Self-hostable later  | Yes (RxServer, SSPL)                                      | Yes (Clojure/JVM, VPS/AWS)                      | Yes (tiny Node WS server)                         | Yes (Docker sync server)                                                       |
| Free tier ceiling    | Core is free forever; paid only for advanced storage/perf | 1GB db, unlimited requests, never paused        | No paid tier exists at all                        | No paid tier exists at all                                                     |
| TypeScript           | Native                                                    | Native                                          | Native                                            | Automerge: bindings over Rust; Yjs: bolted-on `.d.ts`                          |
| Conflict model       | Custom handler, default = drop-fork-use-master            | Field-level merge (`update` vs `merge`)         | CRDT (`MergeableStore`, cell-level LWW)           | True CRDT (automatic merge)                                                    |
| GitHub stars / age   | 23,315 / since 2016                                       | 10,383 / since 2024                             | 5,139 / since 2021                                | Automerge 6,476 (2019); Yjs 22,318 (2014)                                      |
| Integration effort   | Low — drop-in client DB, add sync adapter later           | Lowest — SDK + hosted backend, works in minutes | Low — drop-in store, add WS server for multi-user | Highest — no schema/query layer, you build persistence + sync + React bindings |

**RxDB** — _Verdict: best default choice._ Mature (10 years, largest community here), works with zero backend today, and lets buffi defer the sync-backend decision entirely — when ready, replicate to any REST/GraphQL endpoint or the self-hostable RxServer on Railway. Pros: flexible replication target, deterministic (safe) default conflict handling, strong TS, active releases. Cons: default conflict handling is drop-and-overwrite, not automatic merge — good enough for a low-contention two-person app but would need a custom handler for real concurrent-edit robustness; some production-grade storage engines are paywalled ($99–239/mo) though the free core is likely sufficient at this scale.

**InstantDB** — _Verdict: fastest path to working multi-device sync._ No backend to build at all initially — point the SDK at Instant's hosted free tier (1GB, never paused, no card required) and get realtime sync in minutes; self-hostable later if cost/control becomes a concern. Pros: best "ease of integration" score of any candidate, generous free tier, active daily development. Cons: conflict handling is a manual `merge` helper rather than automatic CRDT merge, so concurrent edits to the same field still need care; self-hosting requires operating a JVM/Clojure service, a different stack than the rest of buffi.

**TinyBase** — _Verdict: leanest, truest CRDT option with zero cost._ Zero backend needed to start, genuinely free forever (no paid tier exists, unlike RxDB/InstantDB), and its `MergeableStore` gives real CRDT-style automatic conflict merging at cell granularity — arguably the best-matched conflict model for a simple `Expense` record. Multi-user sync is a small self-hostable Node WebSocket server, an easy Railway service when the team is ready. Cons: smallest community/ecosystem of the three packaged finalists, less battle-tested at scale, and the query/data model (tabular + key-value) is more minimal than RxDB's document model if the domain grows more complex.

**Automerge/Yjs (hand-rolled)** — _Verdict: best conflict-resolution ceiling, for when control matters more than speed._ Both are the most mature CRDT primitives available (Yjs since 2014, largest star count of any candidate at 22,318) and offer genuine automatic merge with no data-loss risk — the gold standard for "offline robustness." Fully free, fully self-hostable (a one-file Docker sync server for either). Cons: lowest priority-#1 fit — there's no schema layer, no built-in local persistence adapter tuned for an `Expense`-shaped record, and no React query bindings out of the box; the team would be building the equivalent of RxDB/TinyBase's plumbing themselves. Best reserved for if/when the packaged options prove too limiting.
