# TinyBase WsSynchronizer channel: piggyback vs exclusive ownership

Research date: 2026-08-31. This document supports GitHub issue #40, a child of wayfinder map #31 "Safe change mechanism for buffi (schema + client updates)," in `cloud-walker/buffi`.

**Context.** `apps/sync/src/main.ts` creates a bare `ws` `WebSocketServer({ port })`, wraps it with TinyBase's `createWsServer(wsServer)` (no `createPersisterForPath` argument — pure relay mode, no server-side persistence), and handles `SIGINT`/`SIGTERM`. `apps/app/src/appStore.ts` connects with `createWsSynchronizer(appStore, new WebSocket(`${syncUrl}/expense`))` — a plain WebSocket with no subprotocol, and no `channelId` argument (the "legacy," non-multiplexed call form). [docs/research/tinybase-schema-migration.md](/Users/cw/dev/buffi/docs/research/tinybase-schema-migration.md) already establishes, from primary sources, that TinyBase's sync wire protocol carries exactly 8 message kinds (`Response`, `GetContentHashes`, `ContentHashes`, `ContentDiff`, `GetTableDiff`, `GetRowDiff`, `GetCellDiff`, `GetValueDiff` — `src/@types/synchronizers/index.d.ts`) and never carries schema or version data — that finding is taken as given here, not re-derived. [docs/research/client-update-detection.md](/Users/cw/dev/buffi/docs/research/client-update-detection.md) already establishes that `apps/sync` has no HTTP surface at all today. This document asks the next question: given the protocol never carries version data, can an application piggyback its own out-of-band messages (e.g. a real-time schema-version announcement) onto the *same* WebSocket connection/channel TinyBase already owns — and if not, what does TinyBase itself offer as the lightest real-time alternative?

**Method.** All claims below are sourced directly from the `tinyplex/tinybase` GitHub repository — TypeScript source under `src/synchronizers/` (fetched via `raw.githubusercontent.com/tinyplex/tinybase/main/...` and the GitHub Contents API to enumerate the directory tree), `releases.md` (fetched raw and stripped of its HTML rendering), and `src/common/error.ts` — plus tinybase.org's docs site (`guides/error-codes`, `guides/synchronization/using-a-synchronizer`, `api/synchronizer-ws-client/functions/creation/createwssynchronizer`), and the `websockets/ws` package's own `README.md` on GitHub for how a `WebSocketServer` is normally shared across purposes. No blogs, no Stack Overflow, no secondary write-ups were consulted. Source line numbers are against the `main` branch of `tinyplex/tinybase` as fetched on 2026-08-31 and may drift as the repo evolves. The v9.3 changelog entry central to §3 is TinyBase's own PR #177.

## 1. How `createWsServer` attaches to a `ws.WebSocketServer` — additive, not exclusive, at the event level

`createWsServer(webSocketServer, createPersisterForPath?, onIgnoredError?, requestTimeoutSeconds?, fragmentSize?)` takes an already-constructed `ws.WebSocketServer` and, rather than replacing or wrapping it, registers ordinary event listeners on it:

- It attaches an `ERROR` listener to the server itself, and a `CONNECTION` listener via a small internal `addEmitterListener(webSocketServer, event, listener)` helper — which, tracing into `common/other.ts`, is a thin wrapper that just calls the emitter's own `.on(event, listener)`/`.off(...)` — [github.com/tinyplex/tinybase/blob/main/src/synchronizers/synchronizer-ws-server/index.ts#L179-L182](https://github.com/tinyplex/tinybase/blob/main/src/synchronizers/synchronizer-ws-server/index.ts#L179-L182) and [#L641-L666](https://github.com/tinyplex/tinybase/blob/main/src/synchronizers/synchronizer-ws-server/index.ts#L641-L666) (the `CONNECTION` listener registration).
- Because `ws.WebSocketServer` is a Node `EventEmitter`, and `createWsServer` uses plain `.on('connection', ...)` semantics with no `stopImmediatePropagation`-equivalent, **application code can also call `webSocketServer.on('connection', ...)` on the exact same `WebSocketServer` instance passed into `createWsServer`**, and both listeners fire for every new connection, each receiving the same raw `ws.WebSocket`. Node's `EventEmitter.emit()` invokes every registered listener synchronously in registration order with no mechanism for one listener to suppress delivery to another — this is standard, well-established Node semantics, not something specific to `ws` or TinyBase, and `createWsServer`'s source does nothing to work around it (no listener-removal, no wrapping of `webSocketServer.emit`).
- Per accepted connection, `createWsServer` then registers its own per-socket listeners — `addWebSocketListener(client, MESSAGE, ...)`, `addWebSocketListener(client, CLOSE, ...)`, `addWebSocketListener(client, ERROR, ...)` — again via the same plain `.on()`-wrapping helper, once for the "legacy" per-path client path (`addLegacyClient`, [#L578-L598](https://github.com/tinyplex/tinybase/blob/main/src/synchronizers/synchronizer-ws-server/index.ts#L578-L598)) or once for the "multiple" (multiplexed) client path (`addMultipleClient`, [#L600-L639](https://github.com/tinyplex/tinybase/blob/main/src/synchronizers/synchronizer-ws-server/index.ts#L600-L639)), selected by whether the connecting client negotiated the `'tinybase'` WebSocket subprotocol (`client.protocol == WS_SYNCHRONIZER_PROTOCOL`, [#L652](https://github.com/tinyplex/tinybase/blob/main/src/synchronizers/synchronizer-ws-server/index.ts#L652)).

So at the **event-registration** level, the answer is: yes, multiple listeners can coexist on the same `WebSocketServer`'s `connection` event, and even on the same per-client `message` event, exactly as Node's `EventEmitter` allows any number of listeners on any event. That is not, however, the same as being able to piggyback custom *messages* successfully — see §2.

## 2. Why a foreign message on the same per-client socket gets the connection closed, not ignored

Both the server's and the client's per-socket `message` handler run every incoming payload through TinyBase's own decoder, and both close the connection on a payload that doesn't parse as TinyBase's wire format — with no notion of "not for me, ignore and pass through."

- **Server side, legacy client**: `addLegacyClient` wires `addWebSocketListener(client, MESSAGE, (data) => decode(data.toString(UTF8)))` where `decode` comes from `createPayloadDecoder` — [github.com/tinyplex/tinybase/blob/main/src/synchronizers/synchronizer-ws-server/index.ts#L584-L592](https://github.com/tinyplex/tinybase/blob/main/src/synchronizers/synchronizer-ws-server/index.ts#L584-L592). `createPayloadDecoder`'s `decode` function first requires the payload to split into `clientId + '\n' + remainder` via `ifPayloadValid` ([github.com/tinyplex/tinybase/blob/main/src/synchronizers/common.ts#L247-L257](https://github.com/tinyplex/tinybase/blob/main/src/synchronizers/common.ts#L247-L257)); if that fails, or if the remainder doesn't `JSON.parse` into a 3-element `[requestId, message, body]` array whose shape passes `isProtocolMessageValid` ([common.ts#L220-L245](https://github.com/tinyplex/tinybase/blob/main/src/synchronizers/common.ts#L220-L245)) and isn't a recognized fragment continuation either, `decode` calls `invalid()` ([common.ts#L310-L400](https://github.com/tinyplex/tinybase/blob/main/src/synchronizers/common.ts#L310-L400)).
- **Server side, multiplexed client**: `addMultipleClient` wires `handlePayload` from `createMultipleServerClient`, which checks the payload against `ifMultipleControlPayloadValid` (TinyBase's own `Hello`/`Subscribe`/`Unsubscribe` control frames) and `ifMultiplePayloadValid` (a channel-routed data frame); "if `!control && !channel`" — i.e. the payload matched neither shape — it calls `invalidate(errorNew(ERROR_SYNC_MESSAGE))` — [github.com/tinyplex/tinybase/blob/main/src/synchronizers/common.ts#L702-L744](https://github.com/tinyplex/tinybase/blob/main/src/synchronizers/common.ts#L702-L744).
- **Client side**: the client's own `message` handler (`createMultipleState`'s `addWebSocketListener(MESSAGE, ...)`) runs the identical two checks and, symmetrically, calls `invalid(errorNew(ERROR_SYNC_MESSAGE))` when a payload matches neither shape — [github.com/tinyplex/tinybase/blob/main/src/synchronizers/synchronizer-ws-client/index.ts#L678-L728](https://github.com/tinyplex/tinybase/blob/main/src/synchronizers/synchronizer-ws-client/index.ts#L678-L728).
- **What `invalid()`/`invalidate()` actually does**: in every case above, it is wired to `createInvalidPayloadHandler(webSocket, onIgnoredError)`, whose returned handler unconditionally calls `webSocket.close(code, error.message)` on the *first* invalid payload it sees — `1013` if the error is `ERROR_SYNC_OVERFLOW` (code 15), otherwise `1007` (invalid frame payload data) for `ERROR_SYNC_MESSAGE` (code 14) — [github.com/tinyplex/tinybase/blob/main/src/synchronizers/common.ts#L116-L136](https://github.com/tinyplex/tinybase/blob/main/src/synchronizers/common.ts#L116-L136). There is no "ignore and continue" branch; the very first non-conforming payload tears down the connection.
- **Confirmed independently in the changelog**, describing this exact behavior as shipped, not merely intended: "Malformed WebSocket traffic reports error 14 and closes the offending peer with status `1007` before relay; complete messages and multiplex envelopes are limited to 16 MiB, with oversize input closing only its sender" — [raw.githubusercontent.com/tinyplex/tinybase/main/releases.md](https://raw.githubusercontent.com/tinyplex/tinybase/main/releases.md) (v9.3, "Reliability And Hardening" section).
- **Confirmed in the documented Error Codes reference**: code `14` is "A `Synchronizer` protocol message was invalid" and code `15` is "A synchronization capacity limit was exceeded" — [tinybase.org/guides/error-codes](https://tinybase.org/guides/error-codes/) — with the underlying string built as `` `tinybase:${code}` `` by `errorNew` in source — [github.com/tinyplex/tinybase/blob/main/src/common/error.ts#L8-L19](https://github.com/tinyplex/tinybase/blob/main/src/common/error.ts#L8-L19) (`ERROR_SYNC_MESSAGE = 14`, `ERROR_SYNC_OVERFLOW = 15`).

**Consequence**: even though Node's `EventEmitter` (server side) and the WebSocket `EventTarget`/`EventEmitter` API (client side) technically deliver every message to every registered listener — meaning an application-added `message` listener on the *same socket* TinyBase is using would genuinely also receive a foreign payload — that fact is irrelevant in practice, because TinyBase's own listener on that same socket receives that payload too, fails to parse it as its own protocol, and closes the connection outright. There is no filtering, prefixing, or envelope convention by which a foreign message could be made to look "not mine, skip it" to TinyBase's decoder; the decoder's only two outcomes for a payload are "matches my framing" or "kill the connection." **Piggybacking arbitrary custom messages onto the same WebSocket connection/message stream that carries the TinyBase sync protocol is not viable** — it will trigger `ERROR_SYNC_MESSAGE` (code 14) and get that peer's connection closed (status 1007) on the first such message, for both the client-originated and server-originated directions.

## 3. TinyBase's own (documented) multiplexing is real, but it's a channel for more MergeableStores, not a general escape hatch

TinyBase does provide an officially supported way to carry more than one logical sync stream over a single physical WebSocket connection — but it is scoped strictly to *additional TinyBase `MergeableStore` synchronizers*, not arbitrary application messages, and it requires opting into a different (still TinyBase-owned) wire framing, not writing outside it.

- **What it is**: as of **v9.3** (PR #177), "Multiple WebSocket Synchronizers can now share a single physical WebSocket connection... This is useful when an application has several independently synchronized `MergeableStore` instances but needs to limit its connection count." The client creates the WebSocket with the `'tinybase'` subprotocol and passes a `channelId` string as the third argument to `createWsSynchronizer`: `createWsSynchronizer(store, webSocket, channelId, ...)` — [raw.githubusercontent.com/tinyplex/tinybase/main/releases.md](https://raw.githubusercontent.com/tinyplex/tinybase/main/releases.md) (v9.3, "Multiple Stores Over One WebSocket"), matching the "Signature 2" overload documented at [tinybase.org/api/synchronizer-ws-client/functions/creation/createwssynchronizer](https://tinybase.org/api/synchronizer-ws-client/functions/creation/createwssynchronizer/) and the guide's own description: "When an application synchronizes several `MergeableStore` instances, they can share one physical WebSocket" — [tinybase.org/guides/synchronization/using-a-synchronizer](https://tinybase.org/guides/synchronization/using-a-synchronizer/).
- **Source confirms it's the same call path as legacy, gated by an argument-type check**: `createWsSynchronizer` dispatches on whether its third positional argument is a string (`channelId`, → multiplexed `createMultipleWsSynchronizer`) or a number (`requestTimeoutSeconds`, → `createLegacyWsSynchronizer`) — [github.com/tinyplex/tinybase/blob/main/src/synchronizers/synchronizer-ws-client/index.ts#L1128-L1153](https://github.com/tinyplex/tinybase/blob/main/src/synchronizers/synchronizer-ws-client/index.ts#L1128-L1153). The two modes cannot mix on one socket: attempting multiplexed use of a socket already claimed for legacy use throws `ERROR_LEGACY_MULTIPLEX`, and vice versa throws `ERROR_MULTIPLEX_LEGACY` (tracked via a `WeakSet`/`WeakMap` keyed on the `webSocket` instance) — [index.ts#L920-L922](https://github.com/tinyplex/tinybase/blob/main/src/synchronizers/synchronizer-ws-client/index.ts#L920-L922), [index.ts#L992-L995](https://github.com/tinyplex/tinybase/blob/main/src/synchronizers/synchronizer-ws-client/index.ts#L992-L995).
- **Server side requires no extra code for a new channel in relay mode**: `createWsServer`'s `configureServerClient` calls the optional `createPersisterForPath?.(pathId)` callback for each resulting path; if that callback is absent (as in `apps/sync/src/main.ts`, which calls `createWsServer(wsServer)` with no second argument) or returns `undefined` for a given path, the server sets that path's state straight to `Ready` with no `Persister`/`Synchronizer` of its own, and `handleMessage` simply relays incoming payloads to the other clients on that same path — [github.com/tinyplex/tinybase/blob/main/src/synchronizers/synchronizer-ws-server/index.ts#L210-L243](https://github.com/tinyplex/tinybase/blob/main/src/synchronizers/synchronizer-ws-server/index.ts#L210-L243) (configuration) and [#L417-L438](https://github.com/tinyplex/tinybase/blob/main/src/synchronizers/synchronizer-ws-server/index.ts#L417-L438) (`handleMessage`'s pure fan-out to `otherClientId !== clientId` peers). Paths, including new multiplexed-channel paths, are created lazily on first use ([`createPath`, #L496-L507](https://github.com/tinyplex/tinybase/blob/main/src/synchronizers/synchronizer-ws-server/index.ts#L496-L507)) — the existing bare `createWsServer(wsServer)` in `apps/sync/src/main.ts` already relays any path/channel a client opens, with no server-side change required to add one.
- **It is still not a general escape hatch for non-TinyBase data.** The multiplexed frame format itself is TinyBase's own (`createMultiplePayload`/`MultipleControl.Hello|Subscribe|Unsubscribe`, [common.ts#L108-L114](https://github.com/tinyplex/tinybase/blob/main/src/synchronizers/common.ts#L108-L114) and [#L474-L554](https://github.com/tinyplex/tinybase/blob/main/src/synchronizers/common.ts#L474-L554)); a channel only carries what a `WsSynchronizer` puts on it for a `MergeableStore` it's synchronizing (content hashes and table/row/cell/value diffs — the same 8 message kinds established in [docs/research/tinybase-schema-migration.md](/Users/cw/dev/buffi/docs/research/tinybase-schema-migration.md)). There is no API to open a channel and hand it raw/arbitrary bytes instead of a `MergeableStore`'s sync traffic. Neither `guides/synchronization/using-a-synchronizer` nor the API pages for `WsSynchronizer`/`WsServer` mention a custom-message, pass-through, or user-payload extension point of any kind — the multiplexing feature is described and typed purely in terms of "several independently synchronized `MergeableStore` instances," never generic application messages.
- **A documented caveat worth carrying forward if this is ever adopted**: "Channel Ids are not an authorization boundary: a client accepted on a base path can subscribe to any valid descendant channel. Authenticate and isolate untrusted clients by base path, and do not treat client Ids derived from `Sec-WebSocket-Key` as authenticated identities" — [raw.githubusercontent.com/tinyplex/tinybase/main/releases.md](https://raw.githubusercontent.com/tinyplex/tinybase/main/releases.md) (v9.3). Not directly about piggybacking, but relevant to any future design that puts more than one logical stream behind one connection.
- **Sync is push-driven, not poll-driven**, which is what makes this relevant to "real-time": `createCustomSynchronizer` (`src/synchronizers/index.ts`) registers a `persisterListener` that is invoked on local store changes and drives outgoing sync traffic to peers — [github.com/tinyplex/tinybase/blob/main/src/synchronizers/index.ts#L278-L355](https://github.com/tinyplex/tinybase/blob/main/src/synchronizers/index.ts#L278-L355) — so a value change in a synced `MergeableStore` propagates to connected peers as soon as it happens, not on the next poll.

## 4. What the `ws` package itself supports for sharing a server/port across purposes

Node's `ws` documents, in its own `README.md`, a standard pattern for running more than one logical WebSocket endpoint on one HTTP server and port: construct each `WebSocketServer` with `{ noServer: true }`, listen to the underlying `http.Server`'s own `upgrade` event once, and route each upgrade to the right `WebSocketServer` by inspecting `request.url` (path-based dispatch), calling that server's `handleUpgrade(request, socket, head, done)` and then `done`'s callback emitting `'connection'` on the chosen server —

```js
const server = createServer();
const wss1 = new WebSocketServer({noServer: true});
const wss2 = new WebSocketServer({noServer: true});
// ... wss1.on('connection', ...), wss2.on('connection', ...)
server.on('upgrade', function upgrade(request, socket, head) {
  const {pathname} = new URL(request.url, 'wss://base.url');
  if (pathname === '/foo') {
    wss1.handleUpgrade(request, socket, head, (ws) => wss1.emit('connection', ws, request));
  } else if (pathname === '/bar') {
    wss2.handleUpgrade(request, socket, head, (ws) => wss2.emit('connection', ws, request));
  } else {
    socket.destroy();
  }
});
server.listen(8080);
```

— from the "Multiple servers sharing a single HTTP/S server" section of [github.com/websockets/ws](https://github.com/websockets/ws) (`README.md`, `master` branch). This is the standard, primary-source-documented way to run a second, fully independent WebSocket endpoint (its own `WebSocketServer`, its own `connection`/`message` handling, entirely outside TinyBase) on the same port as the TinyBase relay — relevant as the "second connection" alternative in the Recommendation below, and distinct from §1's finding that a single `WebSocketServer`'s `connection` event itself accepts multiple listeners (that's about one server object, not about running two).

`apps/sync/src/main.ts` today constructs its `WebSocketServer` directly with `{ port }` (no `noServer`, no explicit `http.Server`) — [apps/sync/src/main.ts](/Users/cw/dev/buffi/apps/sync/src/main.ts). Adopting the `noServer`/`handleUpgrade` pattern to add a second endpoint would mean introducing an explicit `http.Server` for the first time (still no HTTP request/response surface needed — `noServer` mode never invokes a request handler, only the `upgrade` event), a small but real structural change to a currently 13-line file.

## Summary

**Piggybacking on the same connection/channel — not viable, confirmed from source:**
- `createWsServer`'s attachment to a `ws.WebSocketServer` is additive at the `connection`-event level (ordinary `EventEmitter.on()`, no listener exclusivity) — other code *can* also listen to `connection` on the same server object.
- But per-connection, TinyBase's own `message` listener treats any payload that doesn't match its exact wire framing (legacy `clientId\n[requestId,message,body]` or multiplexed control/channel envelopes) as a protocol violation, calls `webSocket.close()` with status 1007 (`ERROR_SYNC_MESSAGE`, code 14) or 1013 (`ERROR_SYNC_OVERFLOW`, code 15), and does this unconditionally on the very first such payload — both client-side and server-side, confirmed in source (`createInvalidPayloadHandler`, `createPayloadDecoder`, `createMultipleServerClient`, `synchronizer-ws-client`'s message handler) and independently in the v9.3 changelog's own description of this behavior.
- There is no envelope convention, prefix, or documented extension point by which a foreign message could be marked "not TinyBase's, pass through" — the decoder's only two outcomes are "matches my protocol" or "kill the connection."

**TinyBase's own multiplexing (v9.3+) — real, documented, but scoped to more `MergeableStore`s, not arbitrary messages:**
- `createWsSynchronizer(store, webSocket, channelId, ...)` with a `'tinybase'`-subprotocol WebSocket lets multiple independently-synchronized `MergeableStore` instances share one physical WebSocket connection — an officially supported feature (`WsServer`/`WsServerSimple`), not a hack.
- `apps/sync/src/main.ts`'s existing bare `createWsServer(wsServer)` (no `createPersisterForPath`) already operates as a generic per-path relay and needs no server-side changes to relay an additional channel.
- The channel still only carries a `MergeableStore`'s own sync traffic (hashes/diffs), driven by a push-based `persisterListener` on local changes — not raw application bytes.
- Adopting it requires switching the client's WebSocket construction to the `'tinybase'` subprotocol and adding a `channelId` argument — legacy and multiplexed usage cannot mix on the same socket (`ERROR_LEGACY_MULTIPLEX`/`ERROR_MULTIPLEX_LEGACY`), so this is a real (if small) protocol change to `apps/app/src/appStore.ts`'s current call.

**The `ws` package itself — supports cleanly running a second, independent endpoint on the same port:**
- `websockets/ws`'s own README documents `noServer: true` + `handleUpgrade` + manual `request.url`-based routing on a shared `http.Server`'s `upgrade` event as the standard way to run multiple independent `WebSocketServer`s on one port.
- This is a genuinely separate WebSocket connection (its own handshake, its own `connection`/`message` events), not a channel inside TinyBase's protocol — no risk of TinyBase's decoder ever seeing a foreign payload, but a second live socket per client, and (for `apps/sync`) first-time introduction of an explicit `http.Server`.

---

## Recommendation

**Piggybacking custom out-of-band messages directly onto the same WebSocket connection/message stream TinyBase's `WsSynchronizer`/`WsServer` use is not viable** — TinyBase's own decoder, on both ends, treats any non-conforming payload as `ERROR_SYNC_MESSAGE` and closes that connection, by design and as shipped (confirmed in source and independently in the v9.3 changelog). There is no filtering or pass-through option; a custom message sent on the same socket TinyBase is reading from will get that peer disconnected on the first such message, whether the custom traffic goes over the same logical path/channel or a different one within the same connection's message stream.

**The lightest real-time (non-polling) alternative is TinyBase's own multiplexed second channel (§3), not a second WebSocket connection (§4)** — for buffi's specific situation, the multiplexed-channel route is strictly cheaper and already fits the deployed shape:
- **No new connection, no new port, no new `http.Server`.** A second `MergeableStore` (holding nothing but, e.g., a single Value like `schemaVersion`) synced under its own `channelId` (e.g. `createWsSynchronizer(versionStore, webSocket, 'schema-version')` alongside the existing store's channel) shares the exact physical WebSocket the app already opens for `expense` sync. No additional TCP/TLS handshake, no additional connection for Railway's load balancer or the browser's per-origin connection budget to account for.
- **No server-side code change.** `apps/sync/src/main.ts`'s existing `createWsServer(wsServer)` (no `createPersisterForPath`) already relays any path/channel generically — a `schema-version` channel "just works" as a broadcast relay the moment clients start subscribing to it, identical to how `expense` is relayed today.
- **Genuinely real-time, not polling.** Confirmed from source: local changes to a synced `MergeableStore` drive outgoing sync traffic via a `persisterListener` invoked on transaction commit, not on a timer — a `setValue('schemaVersion', ...)` on one client propagates to connected peers as soon as it happens, through the same push mechanism `expense` sync already relies on.
- **Real cost, and it is not free**: this requires migrating the *existing* `expense` synchronizer to the multiplexed call form too, since legacy and multiplexed usage cannot share one socket (`ERROR_LEGACY_MULTIPLEX`/`ERROR_MULTIPLEX_LEGACY`) — concretely, `apps/app/src/appStore.ts`'s `new WebSocket(`${syncUrl}/expense`)` (no subprotocol) and 2-argument `createWsSynchronizer(appStore, ws)` call both need to change (subprotocol `'tinybase'`, base path, and a `channelId` argument on both the existing and new synchronizer). That is a wire-protocol change to production sync, not a purely additive one — worth sizing and testing deliberately, not a drop-in.

**The second-WebSocket-connection route (§4) is the fallback if the multiplexed-channel migration is judged too invasive right now**: run a second `WebSocketServer({noServer: true})` beside the TinyBase one, sharing one `http.Server`/port via `upgrade`-event path routing exactly as `ws`'s own README documents, carrying whatever ad hoc version-announcement message shape buffi wants with zero constraint from TinyBase's framing. Its costs are the mirror image of the channel route: a second live connection per client (extra handshake, extra idle socket, one more thing to reconnect/back off on flaky networks) and, for `apps/sync`, the first-time introduction of an explicit `http.Server` object (still no HTTP request/response handling needed — `noServer` mode only hooks the `upgrade` event) — but it requires zero changes to the existing `expense` synchronizer or its wire protocol, and zero coupling between "is a newer schema available" and TinyBase's own sync machinery.

**Net**: given buffi's stated preference for investing in the structurally cleaner path when there's no deadline pressure, the multiplexed-channel approach (§3) is the better fit *if and when* the `expense` synchronizer's migration to the `'tinybase'`-subprotocol/channelId call form is undertaken anyway — it is the more deeply integrated, zero-extra-connection answer, using only TinyBase's own documented, versioned (v9.3+) feature. If that migration isn't wanted yet on its own merits, standing up an independent second `WebSocketServer` on the same port (§4) is the correct, still primary-source-backed fallback, and touches nothing about how `expense` syncs today.
